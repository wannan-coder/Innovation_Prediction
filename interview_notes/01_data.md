# 面试专题 01 · 数据篇：字段、来源、清洗与去向

> 用途：面试前快速复习“项目数据”这一整块，做到能说清字段含义、数据来源、清洗动机、最终去向。
> 阅读方式：先看第 0 节的 60 秒速记，再按第 2～6 节对应四类实体，最后用第 9 节做模拟问答自测。
> 说明：文中所有企业名、专家名、成果标题均为**按代码字段构造的示例**，结构与处理逻辑真实，数值为示意。

---

## 0.0 先建立正确的心智模型（最重要，先看这段）

把系统想成一个**“产学研 / 科技成果转化平台”的智能顾问**。平台里有两类“供给”：

- **成果库**：一大堆科研成果（来自高校、研究院、其他公司），回答“有哪些现成技术可以拿来用”。
- **专家库**：一大堆科研人员档案，回答“有谁在做相关研究”。

**企业是需求方。** 系统做的事：拿到**一家**企业的信息 → 从公共库里检索出跟它相关的专家和成果 → 让大模型综合这三样，帮这家企业规划未来 2–3 年该做什么研发。

### 常见误解澄清

| 问题 | 正确答案 | 依据 |
|---|---|---|
| 一次预测一个企业还是多个？ | **一次一家企业**。数据集里有很多企业只为训练，样本彼此独立，不存在跨企业推理 | prompt 写“为**该公司**制定”；每条带 `enterprise_index`；逐条循环处理 |
| 专家是谁？为什么有专家？ | 外部**科研人员档案**（非本企业员工），用来提供“研究趋势”信号 | 用企业 business 匹配专家，取其 `application` 写入 `research_field` |
| 科研成果是谁的？ | **不是该企业的**，来自**外部公共成果库**，按相似度匹配而来 | prompt 明确“（**非企业自身的、外部的成果**）” |
| 规模为什么是 1/2/3？谁填的？ | 原始系统里的**编码**，清洗脚本翻译成中文；由**原始数据提供方/业务系统**录入 | `mapping={'1':'小型','2':'中型','3':'大型'}` |

**一句话总结**：对**每家企业单独**预测；输入 = 企业画像 + 从公共**专家库/成果库**检索出的相关方向与外部成果；数字编码是原始录入系统填的，清洗时翻译成中文。

**诚实边界**：
- 能确定：一家一条、专家/成果来自外部公共库、1/2/3 是原始编码。
- 不能确定：三张业务 Excel 最初从哪个平台导出、谁录入 → **需要向导师确认**。

## 0. 60 秒速记（先背这段）

> 项目核心数据有四类：企业、专家、科研成果、企业需求，原始数据由课题组以脱敏 Excel 形式提供。企业数据保留名称、经营范围、行业分类、规模、注册信息等字段；专家数据保留研究方向和应用领域；成果数据保留标题和成果介绍。清洗阶段重点处理重复记录、缺失值、HTML 标签、工商登记模板文本、JSON 字符串、序号与标点混乱，并删除联系人和系统管理字段。清洗后，先把企业转成企业画像文本，再用向量相似度匹配专家与成果，最终组装成 `company_info`、`research_field`、`achievement` 三个字段供大模型训练。外部学术数据方面，项目用 arXiv API 抓取论文，并用 ADS、OpenAlex、Crossref 与期刊分级映射补充元数据。

**一条必须记住的口径**：`research_field` 在当前主链路里主要来自**匹配专家的 `application` 字段**；arXiv 是已开发但未在主链路显式接入的补充模块。不要声称“研究趋势全部来自 arXiv”。

## 1. 数据全景

### 1.1 四类业务数据

| 数据类型 | 原始文件 | 作用 |
|---|---|---|
| 企业数据 | `Dataset/enterprises_full.xlsx` | 定义“这是一家什么企业” |
| 专家数据 | `Dataset/experts_full.xlsx` | 补充可能相关的研究方向 |
| 科研成果 | `Dataset/needs_achievements_full.xlsx` | 提供可借鉴、可转化的具体技术成果 |
| 企业需求 | `Dataset/needs_achievements_full.xlsx` | 技术需求，目前不进入 SFT 主输入 |

> 成果和需求原始在同一张表，通过 `contect_type` 区分：`1 = 成果`，`2 = 需求`（字段名本身就是历史拼写，面试不必纠结成 content）。

### 1.2 外部学术数据

| 数据 | 来源 | 作用 |
|---|---|---|
| 论文元数据 | arXiv API | 补充学术研究趋势 |
| 期刊/会议等级 | CCF、CAS、JCR 本地映射表 | 评价论文来源质量 |
| 期刊、引用量 | NASA ADS、OpenAlex、Crossref | 补充发表与引用信息 |

### 1.3 最终送入模型的核心字段

```json
{
  "company_info": "企业画像文本",
  "research_field": "相关研究方向（来自匹配专家）",
  "achievement": "相关科研成果"
}
```

## 2. 企业数据

**对应代码**：`data_process/enterprises_full_clean.py`、`data_process/enterprise_excel_to_jsonl.py`

### 2.1 关键字段

| 字段 | 含义 | 用途 |
|---|---|---|
| `org_name` | 企业名称 | 标识、去重 |
| `business` | 经营范围/主营业务 | 判断能做什么 |
| `category` / `category_big` / `category_middle` | 行业分类 / 大类 / 中类 | 行业定位 |
| `scale` | 企业规模 | 资源能力 |
| `address` | 地址 | 企业画像 |
| `reg_capital` | 注册资本 | 企业画像 |
| `company_org_type` | 企业性质 | 国企/民营/有限责任等 |
| `establish_time` | 成立时间 | 企业画像 |

### 2.2 原始记录示例

```json
{
  "id": "93821",
  "org_name": "杭州智造科技有限公司",
  "scale": "2",
  "business": "一般经营项目是：工业机器人研发、生产、销售；智能制造系统集成（依法须经批准的项目，经相关部门批准后方可开展经营活动）\n",
  "address": "浙江省杭州市滨江区",
  "reg_capital": "5000万元",
  "company_org_type": "有限责任公司（自然人投资或控股）",
  "estiblish_time": "2018-05-16 00:00:00",
  "category": "高端装备制造；",
  "category_big": "制造业。",
  "category_middle": "智能制造设备",
  "logo_url": "https://xxx/logo.png",
  "linkman_email": "zhangsan@example.com",
  "create_time": "2024-01-01"
}
```

典型问题：
1. 大量与建模无关的管理字段（`id`、`logo_url`、`create_time`）。
2. 敏感字段（联系人邮箱）。
3. `scale` 用数字编码。
4. `estiblish_time` 拼写错误。
5. 时间含无用的时分秒。
6. `company_org_type` 括号说明过细。
7. `business` 含工商登记模板、换行、括号免责声明。
8. 行业字段有多余标点。

### 2.3 清洗后示例

```json
{
  "org_name": "杭州智造科技有限公司",
  "scale": "中型",
  "business": "工业机器人研发、生产、销售；智能制造系统集成",
  "address": "浙江省杭州市滨江区",
  "reg_capital": "5000万元",
  "company_org_type": "有限责任公司",
  "establish_time": "2018-05-16",
  "category": "高端装备制造",
  "category_big": "制造业",
  "category_middle": "智能制造设备"
}
```

### 2.4 清洗规则对照

| 原始问题 | 清洗方案 |
|---|---|
| 企业重复 | 按 `org_name` 去重，保留第一条 |
| 空值/NaN | 统一转为空字符串 |
| 无效字段 | 删除 ID、状态、联系人、日志、图片等字段 |
| 字段拼写错误 | `estiblish_time` → `establish_time` |
| 规模数字编码 | `1→小型`、`2→中型`、`3→大型` |
| 时间格式混乱 | 只保留 `YYYY-MM-DD` |
| 企业性质过细 | 删除括号及括号后内容 |
| 经营范围有模板 | 删除“许可经营项目”“一般经营项目”等 |
| 控制字符 | 删除换行、制表符、乱码替代字符 |
| 行业字段脏数据 | 删除末尾标点和多余空格 |
| 行业字段是纯数字 | 整条记录删除 |

### 2.5 如何变成模型输入

`enterprise_excel_to_jsonl.py` 拼成自然语言：

```text
杭州智造科技有限公司，成立于2018-05-16，位于浙江省杭州市滨江区，
是一家有限责任公司，规模为中型企业。
主营业务包括：工业机器人研发、生产、销售；智能制造系统集成。
所属行业领域为：高端装备制造 | 制造业 | 智能制造设备。
注册资金：5000万元。
```

保存为：

```json
{ "enterprise_index": 17, "company_info": "杭州智造科技有限公司，成立于2018-05-16……" }
```

> `enterprise_index` 是关联键：后续专家匹配、成果匹配的结果都靠它挂回同一家企业。

## 3. 专家数据

**对应代码**：`data_process/experts_full_clean.py`、`data_process/enterprises_match_experts.py`

### 3.1 关键字段

| 字段 | 含义 | 后续用途 |
|---|---|---|
| `user_name` | 姓名 | 结果追溯 |
| `research_field` | 研究方向 | 语义相似度计算 |
| `application` | 技术应用领域 | 匹配 + 作研究趋势上下文 |
| `duty` | 职务 | 专家画像 |
| `professional_title` | 职称 | 清洗时并入 `duty` |
| `college` | 学院/单位 | 清洗时并入 `btype_name` |
| `btype_name` | 类别 | 专家画像 |
| `brief_intr` / `introduction` | 简介/详细介绍 | 完整性校验 |

### 3.2 原始记录示例

```json
{
  "id": "10086",
  "user_name": "张教授",
  "research_field": "1. 工业视觉检测；2、机器学习；（3）智能机器人",
  "application": "[\"智能制造,质量检测\",\"机器人,自动化产线\"]",
  "duty": "实验室主任、博士生导师",
  "professional_title": "教授",
  "college": "自动化学院",
  "btype_name": "高校专家",
  "brief_intr": "长期从事工业视觉研究",
  "introduction": "主持多项相关科研项目",
  "phone": "138xxxx0000",
  "email": "xxx@university.edu.cn"
}
```

典型问题：序号混用、中英文标点混用、`application` 是类 JSON 字符串、职务与职称分列、含隐私字段、常见空字段、甚至只有一个汉字的无效研究方向。

### 3.3 清洗后示例

```json
{
  "user_name": "张教授",
  "research_field": "工业视觉检测,机器学习,智能机器人",
  "application": "智能制造,质量检测;机器人,自动化产线",
  "duty": "实验室主任；博士生导师；教授",
  "btype_name": "高校专家自动化学院",
  "brief_intr": "长期从事工业视觉研究",
  "introduction": "主持多项相关科研项目"
}
```

### 3.4 关键清洗逻辑

**研究方向**：`1. 工业视觉检测；2、机器学习；（3）智能机器人` → `工业视觉检测,机器学习,智能机器人`
- 删除 `1.` `1、` `[1]` `（1）` `1)` 等序号与 `●◆` 等项目符号
- 删除空白换行，分隔符统一为逗号

**应用领域**：`["智能制造,质量检测","机器人,自动化产线"]` → `智能制造,质量检测;机器人,自动化产线`
- 只把**引号外**用于分隔数组项的逗号改成分号，引号内逗号保留（属于同一描述）

**职务**：`duty="实验室主任、博士生导师"` + `professional_title="教授"` → `实验室主任；博士生导师；教授`

**删除不完整记录**：`user_name` / `research_field` / `brief_intr` / `introduction` 任一为空则删除；并删除只有一个汉字的研究方向（如 `"学"`）。

### 3.5 如何进入模型

匹配文本 = `research_field + application`。匹配成功后：

```json
{
  "enterprise_index": 17,
  "matches": [
    { "score": 0.84,
      "expert": { "user_name": "张教授",
                  "research_field": "工业视觉检测,机器学习,智能机器人",
                  "application": "智能制造,质量检测;机器人,自动化产线" } }
  ]
}
```

`append_matches_to_inputs.py` 主要取专家 `application`，写入 `research_field`：

```json
{ "research_field": "智能制造；质量检测；机器人；自动化产线" }
```

> **易被追问**：为什么字段叫 `research_field`，实际拼的是 `application`？
> 答：这是把专家的 application 作为“研究方向可落地场景”的代理字段，因为它比纯 research_field 更贴近企业业务；字段名沿用早期设计，语义不够严格，是后续要重命名或双字段保留的技术债。

## 4. 科研成果数据

**对应代码**：`data_process/split_needs_achievements.py`、`data_process/achievements_full_clean.py`、`data_process/enterprises_match_achievements.py`

### 4.1 一条原始成果示例

```json
{
  "contect_type": "1",
  "title": "成果：基于深度学习的工业产品表面缺陷检测方法",
  "analyse_contect": "<p>本成果针对工业零部件表面缺陷检测问题。</p>\n◆ 支持小样本训练\n◆ 可识别划痕、裂纹和凹坑",
  "application": "[\"汽车零部件\",\"3C制造\",\"精密加工\"]",
  "aplication_field_scenario": "[{\"title\":\"生产检测\",\"describe\":\"用于工业产线在线质量检测\"}]",
  "main_function": "<p>自动定位并分类产品缺陷</p>",
  "main_advantage": "<p>检测速度快，标注成本低</p>",
  "scene_lable": "智能制造；视觉检测、质量控制",
  "chain_lable": "工业软件/智能装备",
  "link_name": "李老师",
  "link_tel": "138xxxx0000",
  "create_time": "2023-10-12"
}
```

典型问题：标题带“成果：”、HTML 标签与 `&nbsp;`、项目符号与序号不统一、字段以 JSON 字符串存储、标签标点混乱、含联系人/状态/时间等无关字段、存在测试成果与重复标题。

### 4.2 清洗后关键字段

```json
{
  "title": "基于深度学习的工业产品表面缺陷检测方法",
  "analyse_contect": "本成果针对工业零部件表面缺陷检测问题。1.支持小样本训练；2.可识别划痕、裂纹和凹坑。"
}
```

关键处理：
- 删除标题中的“成果：/成果:”
- 删除 HTML 标签但保留内部文本，删除 `&nbsp;`
- `◆●` 与各种序号统一为 `1.`、`2.`
- 合并换行、补句号
- 按 `title` 去重
- 删除测试数据（如“测试供给”）
- 删除 `analyse_contect` 为空或为“无”的记录
- 删除 title 与 analyse_contect 完全相同的记录

### 4.3 企业匹配成果

企业查询文本：
```text
杭州智造科技有限公司；工业机器人研发、生产、销售；高端装备制造；制造业；智能制造设备
```
成果候选文本：
```text
基于深度学习的工业产品表面缺陷检测方法；本成果针对工业零部件表面缺陷检测问题；支持小样本训练；可识别划痕、裂纹和凹坑
```
两者编码为向量后计算余弦相似度，Top-K 返回：

```json
{
  "enterprise_index": 17,
  "matches": [
    { "index": 326, "score": 0.83,
      "achievement": {
        "title": "基于深度学习的工业产品表面缺陷检测方法",
        "analyse_contect": "本成果针对工业零部件表面缺陷检测问题……" } }
  ]
}
```

拼接为：
```text
成果1：基于深度学习的工业产品表面缺陷检测方法————本成果针对工业零部件表面缺陷检测问题……
```

## 6. 外部学术数据

**对应代码**：`arxiv_process/arxiv_scraper.py`、`arxiv_process/ccf_mapping.py`、`arxiv_process/cas_jcr_mapping.py`

- 论文通过 **arXiv API** 抓取，字段包括 `arxiv_id / title / authors / abstract / doi / categories`。
- 期刊、引用量依次尝试 **NASA ADS → OpenAlex → Crossref**。
- 期刊/会议等级通过本地 **CCF / CAS / JCR** 映射表匹配，输出 `journal_level`。
- 结果按 `pub` 分为 `no_pub`、`arxiv_only`、`published_journals` 三类保存。

> `arxiv_scraper.py` 需要环境变量 `ADS_TOKEN`（NASA ADS API token），无 token 会直接报错。

## 8. 数据来源的诚实口径（重点）

**仓库能明确证明的**
- 企业以 `enterprises_full.xlsx` 提供、专家以 `experts_full.xlsx` 提供、成果与需求以 `needs_achievements_full.xlsx` 提供
- arXiv 论文来自 arXiv API
- 期刊/引用来自 NASA ADS、OpenAlex、Crossref
- CCF/CAS/JCR 来自本地映射表
- chosen/rejected 由兼容 OpenAI API 的大模型生成

**仓库无法证明的**
- 三张业务 Excel 最初来自哪个网站或业务平台

因此**不要**随口说“爬取自企查查/知网/某政府平台/真实合作企业”，一旦被追问接口、合规、采集方式极易穿帮。

**最稳妥口径**（若确为课题组提供）：
> 核心企业、专家、需求和成果数据由课题组已有数据资产以脱敏 Excel 形式提供，我负责字段分析、隐私字段删除、数据清洗与下游建模；外部论文数据由 arXiv API 获取，并用 ADS、OpenAlex、Crossref 与期刊分级映射补充元数据。

**必须先确认的问题**：`enterprises_full.xlsx`、`experts_full.xlsx`、`needs_achievements_full.xlsx` 最初来自哪里？这是数据部分目前唯一无法从仓库得出的关键事实。

## 9. 高频追问与参考回答

**Q1：为什么删除那么多字段？**
> 任务只关注企业业务与技术方向；ID、日志、二维码、联系人、电话、内部状态既无有效语义，又增加噪声或隐私风险。字段保留标准是“能否提升企业画像 / 研究方向 / 成果描述”，不是越多越好。

**Q2：为什么不把所有字段直接拼给大模型？**
> 无关字段占用上下文、分散注意力，还可能让模型关注注册状态、联系人等无关信息；过长输入还会增加成本与截断风险。因此保留任务相关的最小充分信息。

**Q3：清洗会不会误删有用信息？**
> 会有风险。例如删括号可能连带删掉技术限定，删序号可能影响“3D打印”这类含数字词。所以规则清洗后要做字段非空率、文本长度分布和人工抽样复核，并保留原始字段与清洗版本便于回溯。

**Q4：如何验证清洗质量？**
> 1）清洗前后行数/字段数；2）关键字段非空率；3）重复率与无效值占比；4）随机抽样人工比对。不能以“跑完没报错”当作清洗正确。

**Q5：为什么原始数据不放 GitHub？**
> 原始数据可能含企业内部字段、专家联系方式或合作数据，且规模较大，因此仓库只保留处理代码，不公开原始数据；正式使用还需脱敏与权限控制。

**Q6：如何避免数据泄漏？**
> 按企业或行业维度划分，避免同一企业的相似改写同时进入训练和测试；涉及论文趋势时按时间切分，避免用未来论文预测历史时期。

**Q7：四类数据哪个最重要？**
> 企业数据定义应用场景，专家数据提供研究方向，成果数据提供可落地技术抓手，三者缺一会让输出变泛；企业需求目前更多用于后续“需求—成果匹配”扩展。
