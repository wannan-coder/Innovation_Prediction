## 0. 先说清楚：“用什么数据集评估”到底是什么意思

### 0.1 评估要有一份“带参考答案的题”

训练是“给模型看题和答案，让它学”。评估是“给模型看**新的**题，让它答，再和标准答案对分”。

所以评估数据集 = 一堆 **（输入, 参考答案）** 对：

```text
输入:      企业信息 + 研究趋势 + 相关成果
参考答案:  一份人工/大模型写的“标准研发方向”（含战略价值、技术路线）
```

评估流程：

```text
把输入喂给模型
  -> 模型生成预测
  -> 用指标把“预测”和“参考答案”比较
  -> 得到分数（PPL / BLEU / ROUGE / BERTScore / 语义相似度）
```

### 0.2 为什么要分 训练/验证/测试

| 集合 | 作用 |
|---|---|
| 训练集 train | 学参数 |
| 验证集 val | 调参、早停、选最优权重 |
| 测试集 test | **只用来最终报告成绩**，不参与任何调参 |

**关键：测试集必须是模型没见过的。** 如果测试样本参与过训练，就是“背答案”，分数虚高（数据泄漏）。

### 0.3 两类评测方式

| 方式 | 怎么评 | 指标 |
|---|---|---|
| 似然型 | 给参考答案，算模型给它的概率 | **PPL** |
| 生成型 | 让模型自己生成，再和参考答案比 | **BLEU / ROUGE / BERTScore / 语义相似度** |

### 0.4 本项目/面试口径（数据集怎么说）

- 仓库设计：用 SFT 流程切分出的测试集 `model_eval/sample_sft_test.json`。
- 面试可用说法（模拟口径）：

> 我们使用**自建的企业技术创新领域测试集**，从数据里按**行业维度留出**，保证测试行业不参与训练，属于同分布的留出评测集；指标比较 base 模型与微调后模型。

关键点：**"自建领域测试集 + 按行业留出 + 测试不参与训练"**，这三点说清就能应对。

## 1. PPL（困惑度）

### 1.1 是什么

**PPL = 模型对文本的“困惑程度”**，越低表示模型越“不意外”。数值上等于交叉熵的指数。

```text
PPL = exp(L_CE)

L_CE = - (1/N) * Σ_t log P( token_t | token_<t )     # t 遍历答案 token
```

- 只在**参考答案部分**算（prompt 被 mask 掉）。
- PPL = 100 可以粗略理解为“模型平均在 100 个候选里犹豫”。

### 1.2 口径与局限

- **越低越好**。
- 受 **tokenizer、对话模板、截断长度**影响 → 不同设置的 PPL **不能直接横比**。
- PPL 低只代表“模型觉得参考答案更像”，**不等于回答有商业价值**。

---

## 2. BLEU

### 2.1 是什么

衡量**生成文本里有多少 n-gram 出现在参考答案中**（n-gram 精确率），并加简短惩罚。

```text
BLEU = BP * exp( Σ_{n=1..4} w_n * log p_n )

p_n = n-gram 精确率（生成中的 n-gram 有多少出现在参考里）
BP  = 简短惩罚（生成太短会扣分）
BLEU-4 = 只看 4-gram 的版本
```

### 2.2 口径与局限

- 通常取 **0~100**，**越高越好**。
- 局限：**只看字面**；同义改写会被低估；答案越长越吃亏；**不等于正确率**。
- 适合“有固定措辞”的任务，用来做回归对比（微调前后）。

---

## 3. ROUGE

### 3.1 是什么

衡量**参考答案有多少内容被生成覆盖**（召回视角）。

| 变体 | 含义 |
|---|---|
| ROUGE-1 | 一元词（unigram）覆盖率 |
| ROUGE-2 | 二元词（bigram）覆盖率 |
| ROUGE-L | 最长公共子序列（LCS）的 F 值 |

```text
ROUGE-N = (生成与参考共有的 n-gram 数) / (参考里的 n-gram 数)
ROUGE-L = 基于最长公共子序列的 precision/recall/F
```

### 3.2 口径与局限

- 越高越好。
- **中文注意**：`rouge_chinese` 需要中文分词；隔离环境缺该库时常用**字符级**近似，**数值会明显偏高**，面试要主动说明口径。

---

## 4. BERTScore

### 4.1 是什么

用上下文嵌入（BERT 类模型）分别编码预测和参考，对每个 token 找最相似的对方 token，计算：

- **P**（生成里的 token 有多少能被参考匹配）
- **R**（参考里的 token 有多少能被生成匹配）
- **F1**（综合）

```text
对预测的每个 token，取与参考 token 的余弦最大值 -> 平均 = precision
反向同理 -> recall
F1 = 2PR/(P+R)
```

### 4.2 口径与局限

- 通常 **0~1，越高越好**。
- 比 BLEU/ROUGE **更能容忍同义表达**。
- 局限：依赖所选嵌入模型；对事实正确性不敏感。

---

## 5. 语义相似度（Embedding 余弦）

### 5.1 是什么

用句向量模型分别编码预测和参考，算余弦：

```text
sim = (e_pred · e_ref) / ( |e_pred| * |e_ref| )
```

项目用 Qwen 的 Embedding 模型（`Qwen3-Embedding-0.6B`）。

### 5.2 口径

- 通常 **-1~1，越高越好**。
- 反映“整体意思像不像”，适合评估长文本的语义一致。

---

## 6. 指标怎么组合、为什么不能只看一个

| 指标 | 看什么 | 越高/低 | 主要局限 |
|---|---|---|---|
| PPL | 模型对参考答案的似然 | 越低越好 | 受模板/tokenizer 影响 |
| BLEU | 字面 n-gram 精确率 | 越高越好 | 只看字面 |
| ROUGE | 字面覆盖/召回 | 越高越好 | 只看字面；中文口径敏感 |
| BERTScore | 语义 + token 匹配 | 越高越好 | 依赖嵌入模型 |
| 语义相似度 | 整体语义 | 越高越好 | 不保证事实准确 |
| 格式遵循率 | 结构是否合规 | 越高越好 | 只测格式 |

**结论**：生成任务没有单一完美指标，要**多指标 + 人工抽样**。

## 7. 本项目评测实现要点

`model_eval/evaluator.py` 流程：

```text
1. 读配置、读测试集
2. PPL：逐条算参考答案的困惑度
3. 生成：逐条生成预测（BLEU/ROUGE/语义需要）
4. BLEU/ROUGE：比较预测与参考
5. 释放 LLM 显存
6. BERTScore：用 deberta 算 P/R/F1
7. 语义相似度：用 Qwen Embedding 算余弦
8. 保存 summary + details
```

- 模型加载：base 或 base + LoRA 适配器（`model_eval/utils.py`）。
- 输出：`*_summary.json`（汇总）+ `*_details.json`（逐条）。

**已知问题（面试可提）**：
1. `eval_config.yaml` 里 `language: "en"`，但任务是中文，BERTScore 语言配置应校正。
2. 只开 `eval_bertscore` 时不会触发生成阶段，可能没有 prediction。
3. `SemanticEvaluator` 写死 `device="cuda"`，无 GPU 会失败。
4. 训练模板（`\n`）与评测模板（`\n\n输入：\n`）不一致，影响 PPL/生成。

## 8. 面试问答

**Q1：你们怎么评估？**
> 用留出测试集，比较 base 与微调模型：PPL、BLEU-4、ROUGE-1/2/L、BERTScore 和语义相似度，并统计格式遵循率，最后人工抽样看质量。

**Q2：PPL 是越高越好吗？**
> 越低越好，表示模型对参考答案越不“意外”。但它受模板/tokenizer 影响，不能跨设置横比，也不代表答案是好的。

**Q3：BLEU 高说明模型好吗？**
> 只说明字面和格式更接近参考答案，不等于业务正确；要配合语义指标和人工评审。

**Q4：为什么中文 ROUGE 可能虚高？**
> 缺 `rouge_chinese` 时用字符级 ROUGE，且输出格式高度结构化，字符重合多，数值偏高；应说明口径。

**Q5：BERTScore 和语义相似度区别？**
> BERTScore 是 token 级上下文匹配的 P/R/F1；语义相似度是整句句向量的余弦；前者更细，后者更粗。

**Q6：评估数据集怎么划分/防泄漏？**
> 训练/验证/测试分开，测试按行业留出、不参与训练；避免同一企业改写样本同时进训练和测试。

**Q7：只看自动指标够吗？**
> 不够，生成任务要加人工或 LLM-as-Judge，评估相关性、可行性、前瞻性。
